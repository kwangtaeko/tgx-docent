# 실전 적용 기록 — 메뉴 권한형 업무 앱, React Router (2026-10-16)

docent 1.0 전 세 번째 실전 검증. 대상 레포의 소스·분석 결과는 이 레포에 넣지 않았고, 일반화한 문제와 수치만 적습니다. 원본 레포는 읽기만 했고, 스크래치 복사본에서 SKILL.md 흐름을 그대로 따랐습니다(화면 분석·소개는 서브에이전트로). 실행·캡처는 백엔드(Spring)와 DB가 필요해 하지 않았습니다.

## 대상

- `frontend/`(Vite + React + React Router v7 코드 라우터) + `backend/`(Spring Boot) 두 폴더. 루트에 `package.json`·워크스페이스 설정 없음
- 메뉴 이름·순서·권한은 서버가 내려 주고(DB 초기 데이터), 프론트는 메뉴 코드 → 경로 상수 객체만 가짐. 라우트는 그 객체를 `Object.entries(...).map(...)`으로 만들어 스프레드로 붙임
- 메뉴 22개 중 화면이 구현된 것은 7개(나머지는 준비 중 안내 화면), 화면마다 입력 창(모달) 1~3개

## 흐름과 수치

| 단계 | 결과 |
| --- | --- |
| init | 처음: 감지된 프레임워크 없음(루트에 package.json 없음) → 고친 뒤: `app: frontend`, `react-router` |
| 화면 목록 | 감지기: `/` 하나만(나머지 경로는 변수). 고친 뒤 경고로 위치를 알림 → 에이전트 탐색으로 page 7 + 화면 분석에서 찾은 modal 9 = 16화면 |
| 화면 분석 | 16화면, 서브에이전트 4+3개 병렬. 화면당 약 1~2분. 페이지 7개 중 4개는 처음에 하위 화면이 아직 없어 `opens`만 남음(예상된 문제) |
| 소개·워크플로우 | 기능 2(최상위 메뉴 그룹별), 워크플로우 6 |
| 분석 결과 | 입력 71, 버튼 63(글자 없는 행 클릭 2), 메시지 144(자리 표시 41, 묶음 64), `unknowns` 58 |
| 확인 필요 | 58건(DB에 있는 메뉴·권한, 서버 검증 문구의 노출 조건, 데이터로 채워지는 제목·선택지) |
| 산출물 | HTML·README(기본 프리셋) |

## 발견한 문제와 처리

| # | 문제 | 처리 |
| --- | --- | --- |
| 1 | 워크스페이스 설정 없이 `frontend/`·`backend/`로 나눈 저장소에서 앱을 찾지 못함(대안 탐색이 `apps/*`·`packages/*`뿐) | 설정이 없으면 루트 바로 아래 폴더도 앱 후보로 |
| 2 | 경로를 상수 객체에서 만든 라우트를 감지기가 **조용히** 건너뜀 — 22개 메뉴 중 `/` 하나만 나오고 아무 경고가 없었음 | 변수 경로·스프레드로 붙인 자식 라우트가 있으면 `inventory`가 위치와 함께 경고(React Router 코드 라우터·v7 `routes.ts`·Vue Router). 에이전트가 화면을 더하면 경고를 거둠 |
| 3 | 감지기 경고가 "제외한 항목" 아래에 섞여 나옴, 모노레포에서 경고의 경로가 앱 폴더 기준 | `경고:`로 따로, 경로는 프로젝트 루트 기준 |
| 4 | 메뉴 경로의 그룹 이름(프론트 상수)과 메뉴 이름(DB 초기 데이터)이 다른 파일에 있어 근거 하나로 적을 수 없음 — 4개 에이전트 모두 보고. 검증도 메뉴 이름 글자를 보지 않았음 | `menuPath.moreEvidence`, 이름마다 근거 근처에 글자가 있는지 검사(고친 검사가 7화면 모두에서 실제로 빠진 근거를 잡음) |
| 5 | 선택지가 라벨과 떨어진 상수(코드 → 이름 표)에 있어 `options`를 적지 못함, 첫 선택지만 라벨 옆에 있는 경우도 | `fields[].optionsEvidence`, 선택지마다 두 근거 중 한 곳에 있으면 통과 |
| 6 | 표의 행 클릭처럼 글자 없는 동작을 적을 수 없어 하위 화면으로 가는 길이 빠짐 | `actions[].unlabeled`(처리기 위치만 검사) |
| 7 | `section`에 없는 구획 이름을 적어도 통과 | `section`은 `sections`의 제목이어야 함 |
| 8 | 모든 화면을 감싸는 권한 래퍼의 "조회만 할 수 있습니다" 안내를 에이전트마다 다르게 처리(넣음 2, 뺌 2) | 규칙: 공통 래퍼가 띄우는 문구는 공통 레이아웃 |
| 9 | 규칙은 데이터 제목을 `confidence: medium`으로 두라는데 `title`에는 `confidence`가 없음 | 규칙을 스키마에 맞춤(`unknowns`에 적기) |
| 10 | 추가·수정 겸용 창의 제목, 조건에 따라 바뀌는 입력 이름, 붙거나 빠지는 말, 서버 문구의 접두어, 공용 창의 × 닫기·공용 오류 상자의 항목 이름 접두어, DB 시드에만 있는 권한, 세그먼트 토글의 종류가 불분명 | screen-analyzer 규칙 보강 |

## 고치지 않은 것

- (해결) **메뉴로 넘어가는 업무 흐름**: 처음에는 워크플로우 연결을 버튼 동작과 창에서 돌아감만 인정해, 이 앱의 워크플로우 6개가 모두 "화면 → 창 → 같은 화면"이었습니다. 이후 메뉴에 있는 화면(`menuPath`)으로 옮겨 가는 단계를 메뉴 이동 연결로 인정하고 점선으로 그립니다. 앞 화면에서 만든 것을 다음 화면이 쓴다는 근거가 화면 분석에 있을 때만 씁니다(다시 쓴 소개에서 근거 없이 두 메뉴를 이은 흐름 하나를 뺐습니다).
- 화면에 준비 중 안내만 그리는 메뉴(15개)는 탐색 단계에서 사람이 빼야 합니다(규칙에 `screens.exclude` 제안을 적어 둠).
- `/`가 권한에 따라 다른 메뉴로 보내는 리다이렉트 컴포넌트인데 감지기는 화면으로 셉니다(컴포넌트 안의 `<Navigate>`까지는 따라가지 않음). 화면 목록 확인 때 뺐습니다.
