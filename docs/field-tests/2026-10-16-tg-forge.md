# 실전 적용 기록 — 데스크톱 앱 모노레포 (2026-10-16)

docent 1.0 전 두 번째 실전 검증. 대상 레포의 소스·분석 결과는 이 레포에 넣지 않았고, 일반화한 문제와 수치만 적습니다. 원본 레포는 읽기만 했고, 스크래치 복사본에서 SKILL.md 흐름을 그대로 따랐습니다(화면 분석·소개는 서브에이전트로, 캡처는 데스크톱 앱이라 건너뜀).

## 대상

- pnpm·Turbo 모노레포(`apps/*`, `packages/*`). 화면이 있는 것은 Electron 데스크톱 앱 하나(React 19 + Vite, 라우터 없음)
- 왼쪽 메뉴 6개로 본문을 바꾸는 구조(`useState`의 `view` 값), 메인 프로세스 기능은 `window.forge`(preload)로 호출
- 로그인 없음

## 흐름과 수치

| 단계 | 결과 |
| --- | --- |
| init | 처음: 감지기 0, 앱 후보 없음(루트 기준 설정) → 고친 뒤: `app: apps/desktop`, "데스크톱 앱(electron)" 안내 |
| 화면 목록 | 감지기 0. 에이전트 탐색으로 page 1 + view 5 = 6화면 |
| 화면 분석 | 6화면, 서브에이전트 4개 병렬. 화면당 약 1.5~3분, 모두 `validate <화면ID>` 통과(수정 0~1회) |
| 소개·워크플로우 | 기능 6, 워크플로우 3(새 프로젝트 생성, 기존 프로젝트 업그레이드, 개발 환경 진단) |
| 확인 필요 | 30건(카탈로그 데이터로 채워지는 문구, 메인 프로세스 오류 문구, 외부 서비스 응답) |
| 실행·캡처 | 건너뜀(Electron은 브라우저로 띄울 수 없음) |
| 산출물 | HTML·README·PDF·PPTX(handover) |

## 발견한 문제와 처리

| # | 문제 | 처리 |
| --- | --- | --- |
| 1 | 모노레포에서 감지기가 맞는 앱이 없으면 하위 앱을 전혀 찾지 못함(라우터 없는 React 앱) | 화면 라이브러리(React·Vue·Svelte 등)나 데스크톱 런타임을 쓰는 워크스페이스 폴더를 후보로 |
| 2 | 데스크톱 앱인지 알리지 않아 실행·캡처 단계에서 헤맬 수 있음 | Electron·Tauri면 "소스만으로, 캡처는 건너뜀" 안내, SKILL에 반영 |
| 3 | 주소 없이 메뉴로 바뀌는 화면을 나타낼 종류가 없음 | 화면 종류 `view`(부모 page와 같은 주소, 메뉴로 전환). 목록·상세에 "부모 주소 · 메뉴로 전환" |
| 4 | 실행 중 값이 채워지는 문구(템플릿 문자열)를 통째로 적을 수 없어 조각만 남음 — 6화면 모두에서 보고 | 근거 검사가 `{이름}` 자리 표시를 받음(나머지 글자는 순서대로 있어야 함) |
| 5 | 고정 선택지를 적을 곳이 없음 | `fields[].options`(근거 근처에 글자가 있어야 함), HTML 칩·PPTX 설명 |
| 6 | 카드마다 같은 라벨("취소", "공개 범위")이 반복돼 구분 불가 | `actions[].section` 추가, 필드·버튼에 구획 표시 |
| 7 | 버튼 근거를 처리 코드로 두면 라벨 검사에 실패 | 규칙: `evidence`는 라벨 줄, 처리 코드는 `readFiles`로 |
| 8 | 조건에 따라 바뀌는 버튼 글자, 공통 오류 띠의 메시지, 읽기 전용 값, 주의 문구, `required` 기준이 불분명 | screen-analyzer 규칙 보강 |
| 9 | 큰 공용 파일(메인 프로세스)을 `readFiles`에 넣어 거의 모든 변경에 재분석 | 규칙: 결과를 보여 주는 가장 작은 파일을 고름 |
| 10 | 워크플로우 검증이 `view`의 부모로 "닫고 돌아가는" 연결을 허용(사이드바 전환인데) | 닫고 돌아감은 모달·팝업만. summary-writer 규칙도 보강 |
| 11 | 산출물 이름이 모노레포 루트 패키지 이름(내부 이름) | `output.projectName` > 앱의 제품 이름(package.json·electron-builder·Tauri `productName`) > package.json name |
| 12 | 화면 목록 표의 ID·메뉴 칸이 글자마다 줄바꿈 | ID·화면·경로·메뉴 칸은 줄을 바꾸지 않음 |
| 13 | `type="url"` 입력 종류 없음 | `url`·`tel` 추가 |

## 새 규칙으로 다시 분석

위 규칙을 반영한 뒤 6화면을 모두 다시 분석했습니다(`/docent-analyze all`과 같음, 서브에이전트 4개 병렬).

| | 처음 | 다시 분석 |
| --- | --- | --- |
| 메시지 | 200 | 220(빠졌던 문구를 찾아 늘어남) |
| 문구 조각으로 남은 메시지 | 다수 | 0 — `{이름}` 자리 표시 55개 |
| 묶음(`group`)으로 정리된 메시지 | — | 149(묶음 30개, 표로 보임) |
| 같은 라벨을 구획으로 구분한 버튼 | 0 | 환경 진단 6, 생성 콘솔 14 등 |
| 근거로 넣은 메인 프로세스 전체 파일 | 4화면 | 0(작은 파일로 바꾸거나 `unknowns`로) |

다시 분석하며 더 고친 것: 자리 표시 이름에 띄어쓰기 허용, 자리 표시가 차지하는 소스 글자 160자까지, 문장 중간 조건 문구는 `{A/B}`, 묶음은 같은 종류 셋 이상부터, 묶음 없는 문구가 5개를 넘으면 표로, 자리 표시는 흐린 칩으로 표시.

## 고치지 않은 것

- (해결) 버튼 결과를 뒷받침하는 다른 위치는 이후 `actions[].effectEvidence`로 적을 수 있게 했습니다.

- 상태 이름을 표에서 가져와 문장 앞에 붙이는 문구(`${status}: ${reason}`)는 상태별로 나눠 적지 못하고 `{상태}` 자리 표시 하나로 적습니다(나오는 상태는 `when`에).
