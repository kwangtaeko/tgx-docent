당신은 화면 분석 결과만 보고 이 시스템을 처음 보는 사람에게 소개하는 글과, 사용자가 화면을 오가며 일하는 흐름을 정리합니다. 소스 코드는 읽지 않습니다. 근거는 화면 JSON입니다.

## 입력 (호출할 때 전달받음)

- 프로젝트 루트 경로(읽을 파일: `.docent/inventory.json`, `.docent/screens/*.json`)
- `SKILL_DIR`: docent 스킬 폴더의 절대 경로
- `DOCENT`: docent CLI 실행 명령. 대상 프로젝트 루트에서 실행합니다

## 출력

`.docent/summary.json` (스키마: `<SKILL_DIR>/schemas/summary.schema.json`, 문체: `<SKILL_DIR>/references/writing-style.md` — 먼저 읽습니다)

```json
{
  "oneLiner": { "value": "…하는 …시스템입니다", "screens": ["근거 화면 ID", "…"] },
  "features": [{ "menu": "메뉴 1단계 이름", "value": "이 메뉴에서 하는 일", "screens": ["…"] }],
  "workflows": [{ "name": "업무 이름", "description": "흐름 설명", "steps": ["화면 ID", "화면 ID", "…"] }]
}
```

## 규칙

- 모든 문장은 `screens`에 적은 화면들의 `purpose`·`actions`로 뒷받침되어야 합니다. 화면에 없는 기능을 쓰지 않습니다
- `purpose.confidence`가 `low`인 화면만으로 뒷받침되는 기능은 넣지 않습니다. `unknowns`에 기능 플래그·빈 데이터로 지금 열리지 않는다고 적힌 화면도 기능·워크플로우에 넣지 않습니다
- `features`는 메뉴 1단계(`menuPath.value[0]`)마다 하나. 화면 자신의 `menuPath`가 있으면 그것을 씁니다(`parentId`보다 우선). 메뉴가 없는 화면은 부모 화면(`parentId`나 경로상 상위 화면)이 있으면 부모 화면의 메뉴에 넣고, 나머지는 묶어서 "그 밖의 화면"이라는 메뉴 이름으로 하나로 씁니다. `menu`에는 화면에 보이는 메뉴 문구(영문이면 영문 그대로)를 씁니다
- 워크플로우의 연속한 두 단계 `a → b`는 반드시 `a`의 버튼 중 `navigatesTo: b` 또는 `opens: b`가 있거나, `a`가 `b` 위에 뜬 하위 화면(모달·팝업, 닫고 돌아감)이거나, `a`가 창이 아닌 화면(page·view)이고 `b`가 메뉴에 있는 화면(`menuPath`가 있는 page·view)이라 메뉴로 옮겨 가는 것이어야 합니다. 메뉴 이동은 산출물에 점선으로 그려집니다. 창(모달·팝업)에서 바로 메뉴로 갈 수는 없으니 창을 닫고 돌아가는 단계를 먼저 둡니다(`view` 화면은 부모로 돌아가는 연결이 아님). 연결이 없으면 그 흐름을 쓰지 않습니다. 메뉴 이동은 앞 화면의 결과를 다음 화면에서 이어 쓰는 업무(한 메뉴에서 등록한 항목을 다른 메뉴에서 사용)일 때만 쓰고, 이어 쓴다는 근거가 화면 분석에 있어야 합니다(다음 화면의 입력·선택지·버튼 결과 설명이 앞 화면에서 만든 것을 고른다고 적혀 있음). 이름이 비슷해 보인다는 추측만으로 잇지 않습니다. 관련 없는 메뉴를 차례로 둘러보는 것은 워크플로우가 아닙니다
- 워크플로우는 서로 다른 화면 2개 이상을 오가야 합니다. 한 화면 안에서 끝나는 일(같은 화면으로 돌아오는 저장 등)은 워크플로우가 아니라 그 화면의 기능입니다
- 워크플로우는 사용자가 실제로 하는 업무 단위(등록, 수정, 승인 등)로 2~6개 정도. 입력 양식이 없는 소개·포트폴리오 사이트는 방문자가 따라가는 대표 탐색 경로(예: 소개 → 경력 → 프로젝트)를 0~3개 씁니다. 억지로 개수를 채우지 않습니다

다 쓰면 `$DOCENT validate`를 실행해 `summary.json` 문제가 없는지 확인하고 고칩니다.
